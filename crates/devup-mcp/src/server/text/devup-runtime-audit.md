Plan, then verify, a browser run of generated screens at several viewport widths that the consumer project executes (action: plan | ingest | completion). This server never launches a browser or runs a command. Optional templatePath transactionally writes the fixed Playwright runner and minimal package files alongside outputPath. Set projectRoot when planning to bind evidence to the current source digest. Dimension checks bind explicit Figma artifactId/nodeId references to CSS logical DOM sizes at viewports (default 1440/1100/858/390); width tables disclose missing references and report tolerance exceedances only, never multiplying zoom or DPR. plan validates a declarative plan - baseUrl and allowedOrigins, viewports, screens by routePath or by steps that find elements by role and accessible name, testId or text, and geometry checks (no-horizontal-overflow, contained, aligned, spans, visible, hidden, and bounds - size and position against the Figma frame, exact up to 0.5px of rounding) plus page-health, no-clipped-text, interaction, capture and view-transition (follow a link and confirm a view transition ran) - gives it a content id, and writes it under an allowed root with outputPath. Unknown fields, shell strings, other origins and URLs carrying credentials are refused. The consumer runs harness/runtime-audit against it in fresh isolated browser contexts. ingest reads the plan and the report.json it wrote, rejects a report not bound to that plan by id and file hash, recomputes every count from the items, verifies each screenshot's SHA-256, length and decoded width, and separates what it verified from what the executor only declared. A missing item is not-run, never a pass; a viewport with an environment error makes the verdict inconclusive. A visual original exists only at the widths a screen's Figma frame was drawn at.
Before reporting done, run the runtime audit for every confirmed URL at every required width (default 1440/1100/858/390), read the report, fix failures and rerun until every cell passes. Missing cells are not-run and block completion. At drawn widths require rendered completeness and page, section and asset visual comparisons. Check sequence-order and section-layout at every width.

Rendered completeness requires the frame height (default minimum 90%), listed sections and images, visible text contrast (default minimum 1.5:1), and decoded image resources. no-low-contrast-text checks computed text colours against composited ancestor backgrounds, including browser default control backgrounds. Image or unsupported colour backgrounds are inconclusive, never silently passed. image-loaded checks every img and CSS background URL (including pseudo-elements), requiring naturalWidth > 0; lazy images are loaded for the audit. Both checks accept an optional subject scope and run at every audit width in generated plans. native-appearance fails any visible button whose computed appearance is not none without an author-set background and border, or that paints the browser default grey. stale-resources fails any image, script, stylesheet, font or media response with an HTTP status of 400 or more, and any difference in stylesheet content, image URLs or first-section height from a fresh, cache-free load of the same URL; image-loaded also fails images with no painted box or a failed image request.

`links-resolve` checks every same-origin anchor against confirmed URL patterns and existing routes, following concrete dynamic hrefs. The report and screen-plan finalReport include a linkTable and Markdown table; any failing link prevents done.

Selection proof: expect.selected requires semantic group/target locators, attribute aria-current or aria-selected, a true selection value, and 1..12 captured CSS paint values in styles. It checks exactly one visible selected control, actual computed paint, containment and optional content visibility. Use press(target,value) and back/forward/reload(no target/value) steps to test keyboard and browser history. A URL change or stale ARIA alone never proves visual selection. Markup also detects short-page footer gaps.

Motion checks measure intermediate values for marquee, count-up, steps, tabs and reveal, with explicit candidateId and semantic selectors. A reveal check measures an entrance whatever produced it. `motion.target` is the element that carries the entrance (the inner wrapper, not the painted section) and `motion.items` names the animated children of a group. It scrolls toward the target in small steps and records `measured.trigger` and `measured.frames` (start, middle and end opacity/transform, each with a screenshot): a scroll-linked entrance (CSS `animation-timeline: view()`) must be fully shown once the block is inside the viewport or half a screen of it is showing; a timed one must start no more than 1px off screen and not after the block has been fully visible for 400ms. It then scrolls the target out of view and back: content re-hidden while away, a replay on re-entry, or a target that cannot leave the viewport at that size (re-entry unobserved) fails. Then every scenario runs from a fresh load unless `motion.scenarios` narrows the list, each reported under `measured.scenarios`: fast-scroll (fling to the bottom, then the target must be fully shown), reload and history (reload, or leave and go back, with the target on screen: it must never be hidden or displaced), bfcache (the same after a real back/forward-cache restore, in a browser started with the cache on), client-nav (follow `motion.navigate`, a link, and go back in the same document), image-delay and image-failure (images inside the target stalled or aborted: it still reveals at its reserved height), focus (a focused control inside an unrevealed target is painted, on screen and not trapped; `motion.focus` selects the control), reduced-motion (never hidden or moved while entering under prefers-reduced-motion), no-script (present and painted in the page served without JavaScript), stagger (steps between `motion.items` at most 150ms, stagger span 450ms, whole group 1000ms, or `maxStepMs`/`maxSpanMs`/`maxTotalMs`), progress-sync (with `motion.progress` and `motion.items`: each item within 200ms, or `motion.syncToleranceMs`, of the progress line reaching it). A scenario with nothing to observe in the block (no image, no control, no items) is `not-applicable`. One that could not be observed (no link named, a page the browser does not keep in bfcache, scroll not restored) is `unverified` and the check is `inconclusive`, never a pass; with an explicit `scenarios` list an unobservable scenario fails and the scenarios left out are listed in `measured.scenariosNotRun`. Ingest returns `motionEvidence`: one row per motion check per width (frames, trigger, re-entry, scenario statuses, stagger and progress timings, and what is unverified) and one line per candidate, `verified` only with a passing check at a mobile (<=767px) and a desktop (>=1024px) width and nothing left unverified. A no-clipped-content exception requires allowedMarquees naming one verified horizontal translating track; animation elsewhere never exempts a clipped container. Data-binding checks mutate only an explicitly isolated disposable SQLite database and compare baseline, changed, empty and error states across landing/list/detail. Completion independently rechecks source and artifact hashes, SQL snapshots and all required URL/width/motion/binding coverage. It always writes the canonical .devup/completion.json, optionally copying it to outputPath. Exported source alone never establishes application completion; see the completion guide for the staged contract.
